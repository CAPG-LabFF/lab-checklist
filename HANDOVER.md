# HANDOVER — read this first

You have inherited the **Lab Opening & Closing Checklist**. This document assumes you have never
spoken to the person who built it. It tells you what owns the system, how to read the data, and how
to do every routine task. You do **not** need to understand React to keep this running.

---

## 1. What owns the system — two accounts

Everything depends on **two free accounts**, both registered to the same dedicated email. Neither is
a personal account and neither belongs to the institution's IT — deliberately, so no admin can revoke
them and nobody's departure can break the system.

| Account | What it owns | Where to find the login |
|---|---|---|
| **A dedicated Google (Gmail) account** | The Google Sheet (the database) and the Apps Script (the backend) | **⇒ Lab SOP folder / shared password manager. Fill this in:** `______________________` |
| **A GitHub account/organisation** | The code repository and the published website | **⇒ Same place. Fill this in:** `______________________` |

> If those credential locations above are blank, find them **now** and write them in, then commit the
> change. Without them, nobody can fix the site or read new data through the app.

**Sign into the Google account at least once a year.** Google disables consumer accounts that look
dormant. One login per year keeps the Sheet, the script, and the email trigger alive.

## 2. How to read the history

The data is a Google Sheet owned by the Gmail account.

1. Sign into the Gmail account (or open the share link, if set — see below) and open the Sheet.
2. The **`Records`** tab holds every submission, one row each, oldest first:
   `id, timestamp, area, action, partial, overnight, initials, comment, items_json, flags_json, notified`.
   - `timestamp` is generated by the server in ISO 8601 with the Lisbon offset — never the phone's clock.
   - `items_json` is the checklist exactly as it was when submitted, so old records stay accurate even
     after the checklist is reworded.
3. The **`Subscribers`** tab holds email subscribers (see §4).

**Make it readable without the password (recommended):** Sheet → Share → General access → **Anyone
with the link → Viewer**. Then a successor or auditor can read the full history with only the link.
This exposes no write path — writes only go through the locked Apps Script.

You can filter, sort, and print the Sheet directly, or use the app's **Records** tab (date filter +
CSV export per area).

## 3. Change a checklist item (the most common task)

**Checklists are edited in the Sheet now — not in code.** Open the **`Checklists`** tab (editable only
by the lab account; everyone else sees it read-only).

- **Reword an item:** edit its `label` cell. Leave the `id` alone.
- **Reorder items:** drag the rows — **row order is display order**.
- **Add an item:** add a row, pick `area` and `procedure` from the dropdowns, fill `group` + `label`,
  and **leave `id` blank** — the script fills a new unique id automatically at the next publish.
- **Remove an item:** delete the row. (Recoverable — every published version is archived by date in
  the `ChecklistsPublished` tab.)

**Changes go live at the next daily publish (00:00 Europe/Lisbon), not instantly.** A time-based
trigger validates the tab and writes a snapshot to `ChecklistsPublished`; the app reads only that
snapshot. To publish immediately, open the Apps Script editor and run **`publishChecklists()`** once.

**A typo can't break the live checklist.** If a row is invalid (bad `area`/`procedure`, empty `label`,
or an `area`+`procedure` left with zero items), the publish is **rejected**, a `FAILED` row is logged
in `ChecklistsPublished`, and **yesterday's checklist stays live**. Fix the row and it publishes on the
next run (or run `publishChecklists()` again).

> **Never edit or reuse an `id`.** Records store a snapshot of the checklist *as submitted*, keyed on
> ids, so editing a `label` never rewrites past records — but reusing an old id for a different item
> would corrupt how old records display.

- `src/config/checklists.ts` is now only the **seed** (it created the initial tab) and a code record —
  editing it does nothing at runtime.
- To re-generate the seed rows from it: `npm run seed:checklists` → `checklists-seed.tsv`.

## 4. Email notifications — REMOVED

The email-subscription feature was removed. There is no subscription box, no `subscribe`/`unsubscribe`
route, no notifier, and no `MailApp` use anywhere. The **`Subscribers`** tab and the Records
`notified` column were **left in place** (append-only discipline) but are unused and never written to
by the app — do not rely on them, and do not delete them.

If you ever see Google sending 5-minute failure notices from this project, it means an old
**time-based trigger** (`sendPendingNotifications`) is still installed: Apps Script editor → clock
icon (Triggers) → delete it, signed in as the owning account.

## 5. Redeploy the backend WITHOUT breaking the QR codes

When you change `apps-script/Code.gs`, update it in the editor and redeploy like this:

1. Sheet → **Extensions → Apps Script** → paste the new code → **Save**.
2. **Deploy → Manage deployments →** click the **edit (pencil)** on the existing deployment →
   **Version: New version → Deploy.**

This keeps the `/exec` URL identical, so the app and the printed QR codes keep working.

> **Never use Deploy → New deployment for an update.** That creates a *different* `/exec` URL. The app
> would then need `EXEC_URL` changed in `src/api/backend.ts`, and it would not match anything already
> deployed. Always edit the existing deployment.

## 6. If something stops working

**The website is blank or won't load:**
1. Repo → **Actions** tab → is the latest "Deploy to GitHub Pages" run green? If red, open it and read
   the failed step.
2. Repo → **Settings → Pages** → Source must be **GitHub Actions** (not a branch).
3. If you just deployed, wait ~10 min for the `index.html` cache to expire, then hard-refresh.

**The site loads but shows "couldn't reach the server" / no lab states:**
- The Apps Script `/exec` is down or the URL is wrong. Check `EXEC_URL` at the top of
  [`src/api/backend.ts`](src/api/backend.ts) matches the current deployment's Web app URL
  (Apps Script → Deploy → Manage deployments).
- Open the `/exec` URL with `?route=state` appended in a browser — it should return JSON. If it asks
  for authorization or errors, re-check the deployment is **Execute as: Me / Who has access: Anyone**.

**Google sends failure notices every 5 minutes:** an old email trigger is still installed. Apps
Script → clock icon (**Triggers**) → delete `sendPendingNotifications`. (Email was removed; see §4.)

**Nothing writes / "system is busy" errors:** the Sheet or Apps Script authorization may have lapsed.
Sign into the Gmail account, open the Apps Script, and run any function once to re-authorize.

---

## 7. The one rule that breaks everything

**Do not rename the GitHub repository or the organisation.** The site URL
(`https://capg-labff.github.io/lab-checklist/`) is encoded in every QR code physically posted in the labs,
and the repo name is baked into the build (`vite.config.ts` → `base`). Renaming either silently breaks
every printed code. If you must move accounts, keep the **repo name identical** — then only the host
changes, and you regenerate the QR sheet with `npm run qr -- <new-url>` and reprint.

## 8. Moving to a different owner account (if ever needed)

1. Create the new Gmail + GitHub with the **same repo name** (`lab-checklist`).
2. Recreate the Sheet + Apps Script in the new Gmail (see [docs/phase1-backend-setup.md](docs/phase1-backend-setup.md)
   and [docs/phase2-backend-setup.md](docs/phase2-backend-setup.md)).
3. Put the new `/exec` URL into `src/api/backend.ts`, push.
4. Regenerate and reprint the QR sheet with the new URL.
5. Update §1 of this file with the new credential locations and commit.
